我认为如何把用户原始任务拆分成子任务是一个难点，也是一个值得讨论的地方。理想情况下，如果我们能把任务拆分成两个逻辑（比如改后端和改前端）上基本独立的子任务处理起来是最方便，执行起来效果也是最好的，因为这样到代码合并阶段，基本不会产生代码冲突。同时也不会出现一个子任务要依赖前一个子任务执行完才能执行的尴尬。但现实是这个是否能做到？

<br>
现实中可以做到“尽量独立”，但很难保证所有需求都能拆成完全独立的子任务。系统的目标不应该是强行消灭依赖，而应该是：
把必须串行的部分压缩到最小，把可以通过提前约定接口而并行的部分尽量并行。

关键区别在于：很多看似存在的依赖，其实不是“实现依赖”，而是“决策依赖”。
例如前端开发并不一定要等后端写完，它真正依赖的是双方先确定 API 契约。

<br>

有一个想法是给每一个agent添加一个文件锁，这种方案简单粗暴，单有很多问题。例如internal/order/create.go
internal/order/query.go两个任务实际上可能完全不冲突，但按目录锁策略会被迫串行。而且并不是说只要修改了同一个地方就不能agent并发编码了，恰恰相反，这正式我们用git worktree存在的意义，以及用合并解决冲突的代码。而且我认为有些时候两个agent可能会修改同一个文件，但是他们的修改在后面我们可以通过代码合并，在理解代码逻辑的基础上，合并修改，这个时候我们应该愿意让他们并行。
