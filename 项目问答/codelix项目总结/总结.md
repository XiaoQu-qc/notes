### 1.沉淀提cr的提示词
### 回归测试与变更影响分析 Prompt 模板

#### 第一步：准备输入材料（关键！）
在写提示词之前，请在终端执行以下命令，把输出内容复制下来，粘贴到你的提问框中：

git log --oneline -4 （看4个commit的摘要）

git diff origin/master...HEAD （看你当前分支相对于master改动了什么具体代码）

如果你改了数据库表结构，还需要 git diff --staged 或直接贴出DDL语句。

### 角色设定：
你是一位精通[请填入：Java/Go/Python/前端等]的资深系统架构师，尤其擅长回归测试和变更影响分析。

任务目标：
我当前分支有4个新增功能的commit，即将合入master。请严格审查代码变更，重点不在于代码风格，而在于“破坏性”。请找出任何可能影响现有存量功能正常运行的隐患。

项目背景上下文：

本次修改涉及的模块：[例如：用户订单模块]

依赖的核心中间件：[例如：Redis缓存、MySQL、Kafka]

对外提供的接口：[例如：/api/v1/order/create]

审查清单（请按此维度逐条分析）：

兼容性断裂（最高优先级）：

是否有修改了现有接口的入参结构（字段改名、必填改选填、类型变更）？

是否有修改了现有接口的出参结构（字段删除、类型变更）？

数据库是否有DDL变更（加字段、改字段类型）？如果改了，是否有回填脚本或默认值兜底？

业务逻辑副作用：

新增的逻辑中，是否在公共方法里添加了 if-else 条件？这些条件是否可能覆盖并改变原本业务流程的走向？

是否修改了全局缓存Key的生成规则？这会导致缓存雪崩或命中率骤降吗？

是否修改了公共工具类（Utils）中的基础方法？

依赖与顺序风险：

4个commit之间是否存在编译/启动依赖（即必须按顺序部署）？

本次改动是否涉及第三方接口调用？如果第三方超时或报错，是否有降级方案，是否会拖垮主线程？

并发与数据一致性：

新增功能涉及的表/字段，是否与旧功能存在锁竞争或事务嵌套风险？

输出格式要求：
请按 【高风险-必须修改】、【中风险-建议修改】、【低风险/疑问】 三级分类输出。
对于每个风险点，请直接贴出对应的代码行，并解释为什么现有的其他功能会受牵连。

### 第三步：进阶玩法（让Agent直接“模拟运行”）
如果你想让审查更深度，可以在提示词末尾加上这一段“王炸”指令：

额外指令（模拟回归）：
请基于我的 git diff，不要只看改动行，请向上追溯调用链。找到这些改动方法（Function/Method）的上层调用方。请列出所有可能调用到这些修改点的已有业务流程（例如：支付回调、定时任务、管理后台列表），并判断它们的运行结果是否会因本次改动而发生变化。
